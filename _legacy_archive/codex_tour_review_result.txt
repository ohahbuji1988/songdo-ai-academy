**가장 추천하는 개선은 ‘화면 설명 투어’를 ‘1주차 수업을 고치고 저장하는 짧은 실습’으로 바꾸는 것입니다.** ID 오류는 즉시 고쳐야 하지만, 사용자 피드백의 핵심은 “이 앱으로 무엇을 하면 되는지 모르겠다”는 데 있습니다.

제공된 코드에서 확정할 수 있는 오류와 설계상 개선안을 구분했습니다. 실제 화면·전체 CSS·저장 구현은 확인하지 못했으므로, 현재 가독성과 저장 동작을 단정할 수는 없습니다.

**1. 기술적 진단: ID 오류와 화면 겹침은 별개 문제입니다**

HTML에는 `tour-step-badge`가 있지만 JS는 `tour-badge`를 찾습니다.

```javascript
document.getElementById('tour-badge').innerText = cur.badge;
```

제공된 HTML 기준으로 이 검색 결과는 `null`, 즉 “찾은 요소 없음”입니다. 여기에 글자를 넣으려 하므로 `TypeError`가 발생하고, **해당 함수의 나머지 실행이 중단됩니다.** 아이콘만 바뀌고 제목·설명·강조 영역은 그대로 남는 현상이 생길 수 있습니다.

최소 수정은 다음과 같습니다.

```javascript
document.getElementById('tour-step-badge').textContent = cur.badge;
```

추가로 개발자가 확인할 항목은 다음과 같습니다.

- 화면 요소 생성이 끝난 뒤 투어를 실행하는가?
- `tourStep`이 `0`부터 `tourSteps.length - 1` 범위 안에 있는가?
- 마지막 단계 이후에는 배열을 다시 읽지 않고 투어를 종료하는가?
- 대상 요소가 없거나 접혀 있을 때, 투어만 종료하고 편집은 계속 가능한가?
- 종료할 때 강조 표시와 등록한 이벤트를 모두 정리하는가?

단순히 `?.`로 오류를 숨기면 잘못된 ID가 남습니다. **ID를 바로잡고, 투어 실패가 앱 전체 사용을 막지 않도록 처리해야 합니다.**

`box-shadow: 0 0 0 9999px`는 대상 바깥을 거대한 그림자로 덮는 방식입니다. 대상 주변에 구멍이 뚫린 것처럼 보이지만 다음 문제가 있습니다.

| 원인 | 생길 수 있는 현상 |
|---|---|
| 부모 영역의 `overflow: hidden/auto/scroll` | 그림자가 부모 경계에서 잘려 화면 일부만 어두워짐 |
| 부모가 별도의 화면 겹침 그룹을 만듦 | 대상의 `z-index`를 높여도 다른 영역보다 위로 나오지 못함 |
| 전체 화면 배경막이 대상 위에 있음 | 강조한 대상도 어두워지거나 클릭할 수 없음 |
| 대상이 포함된 영역을 스크롤함 | 별도로 배치한 설명창과 대상의 위치가 어긋남 |

여기서 화면 겹침 그룹은 CSS의 **stacking context**입니다. 같은 건물 안에서 층수를 높여도 옆 건물 위로 올라갈 수 없는 것과 비슷합니다. `transform`, `opacity`, 특정 `z-index` 설정 등이 이런 그룹을 만듭니다. `overflow`의 잘림과는 별개의 문제입니다. [MDN: overflow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow), [화면 겹침 규칙](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Stacking_context)

**권장 구현은 전체 화면 어둡게 처리를 없애고, 대상 테두리와 옆 안내창만 사용하는 것입니다.** 어둡게 처리가 꼭 필요하다면 대상 자체에 거대한 그림자를 붙이지 말고, 앱 바깥의 전용 레이어에서 강조 영역과 안내창을 함께 관리하세요.

**2. 문구: 공간의 이름보다 사용자가 할 행동을 설명하세요**

현재 문구는 제품 구조를 설명합니다.

> “중앙 실시간 캔버스 아트보드”

사용자에게 필요한 설명은 행동과 결과입니다.

> “바꾼 내용이 수업 계획에 반영됐는지 확인하세요.”

“살아 숨 쉬는”, “초록색 링이 감기며” 같은 표현도 삭제하는 편이 좋습니다. 읽는 양에 비해 사용법을 알려주지 못합니다.

첫 화면에는 앱의 목적을 한 문장으로 먼저 보여주세요.

> **6주 AI 수업 계획을 내 수업에 맞게 수정하세요.**  
> 준비된 수업에서 제목과 활동 내용을 바꾸고 저장할 수 있어요.  
> **[예시로 시작하기]**

투어는 다음 네 단계로 권장합니다.

| 단계·위치 | 제목 | 설명 | 다음 단계로 넘어가는 조건 |
|---|---|---|---|
| 1 · 왼쪽 1주차 항목 옆 | **바꿀 수업을 고르세요** | 왼쪽에서 ‘1주차’를 눌러보세요. | 1주차 선택 |
| 2 · 오른쪽 제목 입력칸 옆 | **수업 제목을 바꿔보세요** | 예를 들어 ‘AI로 내 소개 만들기’라고 입력해 보세요. | 제목을 수정한 뒤 ‘계속’ 선택 |
| 3 · 가운데 변경된 제목 옆 | **바뀐 내용을 확인하세요** | 방금 쓴 제목이 수업 계획에 반영됐어요. | ‘확인했어요’ 선택 |
| 4 · 저장 버튼 옆 | **수업 계획을 저장하세요** | ‘저장’을 누르면 지금까지 수정한 내용을 보관할 수 있어요. | 실제 저장 성공 |

세 번째 문구는 **변경 내용이 실제 반영된 뒤에만** 보여줘야 합니다. 네 번째도 저장 성공 응답을 받은 뒤 “저장했어요”로 바꿔야 합니다.

기본 명칭도 함께 바꾸세요.

| 현재 | 권장 |
|---|---|
| 주차 블록 서랍 | 주차별 수업 |
| 캔버스 아트보드 | 수업 계획 미리보기 |
| 속성 편집창 | 선택한 수업 수정 |
| 타이틀 | 수업 제목 |
| 이론 비유 | 쉽게 설명하기 |
| 프롬프트 테크닉 | AI에게 요청하는 방법 |
| 산출물 | 수업이 끝나면 완성할 것 |
| 실시간 동기화 | 바꾸면 미리보기에 바로 반영돼요 |

“교구”처럼 실제 기능 범위를 모르는 단어는 무조건 치환하면 안 됩니다. 파일·준비물·활동 카드 중 무엇을 뜻하는지 확인하고 이름을 붙여야 합니다.

**3. 인터랙션: ‘다음’ 네 번보다 실제 행동 한 번이 중요합니다**

권장 흐름은 **준비된 예시 → 수업 선택 → 내용 수정 → 결과 확인 → 저장**입니다.

- 처음부터 투어를 강제로 띄우지 않습니다. `수정 방법 익히기`로 시작할 수 있게 합니다.
- 안내창은 한 번에 하나만, 해당 버튼이나 입력칸 옆에 표시합니다.
- 사용자가 눌러야 할 요소와 입력한 글자를 가리지 않습니다.
- 안내창에 `1 / 4`, `이전`, `안내 끝내기`를 제공합니다.
- 종료는 “실습 완료”와 구분해 기록하고, 도움말에서 다시 시작할 수 있게 합니다.
- 실습 종료 후에는 바뀐 내용을 그대로 남기고, 실행 취소를 제공합니다.

개발에서는 위치 배치보다 **상태 변화와 연결하는 것**이 중요합니다. 엉뚱한 수업을 눌렀는데 단계가 넘어가거나, 저장에 실패했는데 완료로 표시되면 신뢰를 잃습니다.

안내창 구현 시에는 다음을 포함하세요.

- 스크롤·창 크기 변경 때 위치를 다시 계산합니다.
- 화면 가장자리에서는 안내창 방향을 바꿉니다.
- 대상이 숨겨졌다면 관련 영역을 먼저 열고 표시합니다.
- 키보드만으로 선택·입력·종료할 수 있게 합니다.
- 버튼이 들어간 안내창은 단순 설명용 `tooltip` 대신, 제목이 연결된 비모달 대화상자로 구현합니다. 편집 화면의 키보드 이동을 가두지 않습니다.
- `Esc`로 종료하면 원래 작업 위치로 돌아갑니다.

**4. 전체 UI: 3단 레이아웃보다 ‘문서 편집’이라는 이해가 먼저입니다**

제 판단으로는 **3단 구조를 당장 버릴 필요는 없지만, 미리캔버스를 닮았다는 사실이 사용성을 보장하지는 않습니다.** 사용자는 자유롭게 그림을 배치하려는 사람이 아니라, 수업 내용을 고치려는 사람입니다.

우선 화면을 다음처럼 명확하게 나누세요.

| 왼쪽 | 가운데 | 오른쪽 |
|---|---|---|
| **주차별 수업** | **수업 계획 미리보기** | **1주차 수정** |
| 1~6주차 제목과 짧은 요약 | 실제 결과 문서 | 선택한 수업의 입력칸 |

구체적인 개선 기준은 다음과 같습니다.

- **첫 화면에 완성된 예시를 보여주세요.** 빈 캔버스보다 “이 결과물을 고치는 앱”이라는 이해가 빠릅니다.
- **부가 자료는 접어두세요.** 원칙·요청 예시·수업 자료를 첫 화면에서 모두 펼치지 않습니다.
- **수정창의 기본 항목을 줄이세요.** 제목, 수업 목표, 활동 내용, 완성할 것부터 보여주고 나머지는 `추가 설정`에 둡니다.
- **아이콘에 글자를 붙이세요.** 특히 저장·미리보기·자료는 아이콘만으로 구분하지 않습니다.
- **선택 상태를 색만으로 표시하지 마세요.** 테두리와 함께 `선택됨`, 오른쪽의 `1주차 수정` 제목을 사용합니다.
- **실제 수정창을 가장 읽기 편하게 만드세요.** 가운데 문서를 크게 보여주느라 오른쪽 입력칸이 좁고 작은 상태가 되면 목적이 뒤집힙니다.

시각 설정은 다음 값을 시작점으로 권장합니다. 실제 화면에서 검증해야 하는 제안값입니다.

| 항목 | 권장 시작점 |
|---|---|
| 본문·입력 내용 | 16px |
| 보조 설명 | 14px |
| 영역 제목 | 18~20px |
| 본문 줄 간격 | 글자 크기의 1.5~1.7배 |
| 입력 항목 사이 | 16~24px |
| 버튼 높이 | 40~44px |
| 색상 | 중립색 중심, 초록색은 주요 행동·선택·성공에 제한 |

일반 크기 글자는 배경과 **4.5:1 이상의 명암 대비**를 확보하세요. 연한 회색 설명과 연두색 글자는 실제 색상 조합으로 측정해야 합니다. [W3C 명암 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

창이 좁아지거나 글자를 확대했을 때는 세 영역을 억지로 유지하지 마세요. 왼쪽 목록을 접거나, `수정 / 미리보기` 전환으로 바꾸는 편이 낫습니다.

마지막으로 **“1초 만에 영구 저장”은 현재 코드로 확인되지 않는 약속이므로 삭제해야 합니다.** 웹과 데스크톱에서 저장 위치·보존 방식이 다를 수 있습니다. 실제 구현에 맞춰 `저장 중…`, `저장됨`, `저장하지 못했어요 · 다시 시도`를 보여주세요.

개선 순서는 **① 투어 중단 오류 수정 → ② 목적·명칭 정리 → ③ 실제 수정 실습으로 교체 → ④ 글자·대비·입력창 폭 개선**입니다. 검증할 때는 비전공자에게 별도 설명 없이 “1주차 제목을 바꾸고 저장해 주세요”라고 요청하세요. 투어를 끝까지 읽었는지보다, **도움 없이 수정하고 저장 여부를 이해했는지**가 성공 기준입니다.
